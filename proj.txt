# Executive Summary

Plaur is a production-grade, AI-first Commerce & Marketing Intelligence Operating System that connects deeply to a merchant’s Shopify store, ad platforms, and public social signals to provide continuous, actionable intelligence. Plaur not only reports — it reasons. It explains *why* numbers change, predicts what will happen, recommends prioritized actions, and provides a conversational interface that acts like a human analyst with access to your entire business.

This document is a comprehensive project note covering product objectives, full feature set (detailed), system design, data architecture, AI/ML strategy, security & compliance, infra & devops, rollout strategy, team and resourcing, roadmaps, QA, monitoring, cost drivers, go-to-market and appendices (API scopes, example prompts, weekly report template, and release checklist).

---

# Vision & Goals

**Vision:** Make every merchant feel like they have a senior commerce analyst, CRO expert, and marketing strategist built into their store — accessible via chat.

**Business Goals:**

* Drive measurable revenue uplift for customers via prioritized, data-backed actions
* Become an indispensable subscription product across Shopify merchants (SMB → Enterprise)
* Generate high LTV customers via actionable intelligence and automation

**Product Principles:**

* Data-first, but human-friendly: Every recommendation must be traceable to data and explainable
* Privacy-first integrations and least-privilege access
* Operational safety: no automatic ad/price changes without merchant approval
* Modular: enable/disable data sources and modules per customer

## 1. Global Platform Capabilities

* **Inputs:** OAuth tokens, store data, ad platform tokens, trend signals.

### 1.2 Role-Based Access & Teams

* **Inputs:** User accounts, invitations, SSO (optional).
* **Outputs:** Permissioned UI/controls; action audit logs.
* **Acceptance:** Permission enforcement for sensitive actions and data.

### 1.3 Audit Logging & Activity Timeline

* **Purpose:** Record analyst actions, AI suggestions presented, merchant approvals and changes.
* **Inputs:** System events, user actions, AI recommendations.
* **Outputs:** Tamper-evident logs, exportable timeline.
* **Acceptance:** Logs available via UI and API for 90 days by default.

## 2. Data Integration & Ingestion

### 2.1 Shopify Integration (Full)

* **Purpose:** Ingest products, orders, customers, inventory, themes, discounts, draft orders, webhooks (orders, products), and store settings.
* **What to request:** OAuth scopes covering read_products, read_orders, read_customers, read_inventory, read_themes, read_script_tags, read_content, read_price_rules, write_webhooks (for subscription management), read_apps.
* **Processing:** Incremental sync via webhooks + periodic full snapshots.
* **Outputs:** Normalized canonical store model in data warehouse.
* **Acceptance:** Near-real-time order/stock updates (webhook latency <10s typical), complete snapshot within initial sync window.

### 2.2 Ad Platforms: Meta Ads & Google Ads (Production-Ready)

* **Purpose:** Pull campaign, ad, creative, audience, spending, and conversion metrics.
* **What to request:** OAuth scopes for read-only or read/write as required; ability to map conversions to Shopify orders via conversion APIs and offline conversions.
* **Processing:** Daily incremental pulls, real-time webhook integration where available.
* **Outputs:** Unified ad events feeds, campaign metadata.
* **Acceptance:** 24-hour data freshness for historical trends; near-real-time for critical alerts when conversion webhooks are integrated.

### 2.3 Analytics Integrations (Optional): GA4, Google Search Console, Klaviyo

* **Purpose:** Add session-level context, organic search queries, email campaign performance.
* **Inputs:** GA4 API, GSC, Klaviyo metrics.
* **Outputs:** Enriched session data, channel attribution.

### 2.4 External Trend Feeds

* **Purpose:** Ingest social signals: hashtag velocity, keyword trends, content-type trend data, and public product/category chatter.
* **Sources:** Public APIs, social listening providers, or lightweight third-party trend APIs (no scraping of private data).
* **Outputs:** Trend stream with normalized topics, velocity, sentiment.

### 2.5 Storage & Canonical Data Model

* **Purpose:** Store both raw source payloads and normalized models.
* **Storage:** S3 (raw), RDS/Postgres (normalized transactional), and columnar store (Redshift / Snowflake / BigQuery) for analytics.
* **Acceptance:** Queryable canonical model for any store with documented schema.

## 3. Analytics & Insight Engines

### 3.1 Real-Time Analytics Engine

* **Purpose:** Provide live dashboards and alerting.
* **Implementation:** Stream ingestion via Kafka/Kinesis -> materialized views in ClickHouse/Redshift Spectrum or timeseries DB for low-latency queries.
* **Metrics:** Revenue, orders/minute, conversion rates by source, pageview to checkout conversion.

### 3.2 Time-Series & Anomaly Detection

* **Purpose:** Detect anomalies in revenue, traffic, or ad performance (spikes/drops).
* **Technique:** Seasonal decomposition + Prophet / ARIMA / LSTM ensembles + online detection algorithms (CUSUM, ESD)
* **Outputs:** Anomaly alerts with probable causes and confidence levels.

### 3.3 Cohort, RFM & LTV Models

* **Purpose:** Segment customers for lifecycle actions and value forecasting.
* **Technique:** RFM scoring, probabilistic LTV (BG/NBD + Gamma-Gamma), cohort retention curves.
* **Outputs:** LTV projections, best-customer lists, churn risk lists.

### 3.4 Product & Catalog Analytics

* **Purpose:** SKU-level performance, cannibalization detection, bundle suggestions.
* **Technique:** Uplift modeling, uplift attribution to promotions, conversion funnel for PDP.
* **Outputs:** Product scorecards, suggestions for bundling, price tests.

### 3.5 Trend Mapping & Relevance Scoring

* **Purpose:** Map external trends to product catalog and surface opportunities.
* **Technique:** Semantic matching via embeddings, keyword overlap, taxonomy mapping, and scoring (relevance, speed, business fit).
* **Outputs:** Ranked opportunities with suggested actions.

### 3.6 Marketing Performance Attribution & Correlation

* **Purpose:** Correlate ad spend, creatives, placements with on-site conversions and revenue.
* **Technique:** Multi-touch heuristics + probabilistic attribution + experimental design when data available.
* **Outputs:** Channel/creative-level ROAS, wasteful spend detection.

## 4. AI & Recommendation System

### 4.1 Retrieval-Augmented Generation (RAG) Core

* **Purpose:** Provide conversational, context-aware answers using store + ad + trend data.
* **Components:**

  * Vector store (**Quadrant DB**) with embeddings for: product descriptions, FAQs, historical reports, external trend summaries. Quadrant DB will act as the primary vector database for semantic retrieval, trend–product matching, conversational memory, and recommendation grounding.
  * Retriever that finds top-k context documents by relevance.
  * LLM prompt-engineering and post-processing layers to generate actionable responses.
* **Operational Constraints:** Ensure prompt length remains bounded; provide provenance links for claims.

### 4.2 Recommendation Scoring & Explainability

* **Purpose:** Every recommendation includes: confidence, expected impact, data sources, and steps to implement.
* **Technique:** Decision rules, ML scoring models (XGBoost / LightGBM ensembles), and causal inference where possible.
* **Outputs:** Categorized recommendations (High/Medium/Low impact) with data-backed rationale.

### 4.3 Action Templates & Automated Asset Generation

* **Purpose:** Generate ad copy, product description rewrites, email subject lines, creative briefs and A/B test variants.
* **Constraints:** Provide human-in-the-loop controls and editing before publishing.

### 4.4 Scenario Simulation Engine

* **Purpose:** Run quick “what-if” scenarios (increase spend by 10% on X, run 20% discount) and estimate outcomes.
* **Technique:** Short-run uplift models fed with historical elasticity and seasonality adjustments.

### 4.5 Persistent Memory & Conversation Context

* **Purpose:** Maintain store-specific memory for context across sessions (previous Q&As, accepted recommendations).
* **Controls:** Administrators can clear or export memory. Memory retention policy configurable.

## 8. Billing, Subscriptions & Monetization (Shopify Native)

Plaur uses **Shopify’s official App Billing API (GraphQL)** for all payments and subscriptions. No external payment gateway (Razorpay, Stripe, etc.) is used or required. This ensures full compliance with Shopify App Store policies and builds trust with merchants by charging directly on their Shopify invoice.

### 8.1 Billing Principles

* All charges are processed by Shopify
* Merchants approve charges inside Shopify
* Taxes (GST/VAT), invoicing, and collections are handled by Shopify
* Plaur receives payouts after Shopify commission
* No card data is ever handled by Plaur

### 8.2 Subscription Plans (3-Tier Model)

Plaur offers **three subscription plans**, implemented as Shopify **Recurring App Subscriptions**.

#### 1️⃣ Starter Plan

* Target: Small / early-stage Shopify stores
* Billing: Monthly recurring
* Features:

  * Store health analysis (basic)
  * Limited product & sales insights
  * Limited AI chat queries per month
  * Basic trend analysis (store-level)
  * Weekly reports
* Trial: 14 days

#### 2️⃣ Growth Plan

* Target: Scaling D2C brands
* Billing: Monthly recurring
* Features:

  * Full store analysis (products, collections, pages)
  * Advanced trend analysis (market + category)
  * Social media trend insights
  * Marketing & funnel analysis
  * Meta Ads & Google Ads integration
  * Higher AI chat & report limits
  * Daily insights + weekly deep reports
* Trial: 14 days

#### 3️⃣ Pro Plan

* Target: Large brands & performance-driven stores
* Billing: Monthly recurring
* Features:

  * Everything in Growth
  * Real-time anomaly detection
  * Advanced competitor benchmarking
  * Predictive sales & demand forecasting
  * Unlimited AI chat (fair-use policy)
  * Usage-based AI overage support
  * Priority processing & insights
  * Voice summaries powered by Sarvam API
* Trial: Optional / custom

### 8.3 Usage-Based Billing (Add-on)

For high-volume AI usage, Plaur uses **Shopify Usage-Based Charges**:

* Applied only on Growth & Pro plans
* Monthly capped amount
* Used for:

  * Extra AI chat queries
  * Large-scale report generation
  * Heavy data re-analysis

Usage charges are transparently added to the merchant’s Shopify bill at the end of the billing cycle.

### 8.4 Billing Flow

1. Merchant installs Plaur
2. Plaur checks active subscription status
3. If no active plan → redirect to Shopify billing approval
4. Merchant approves plan inside Shopify
5. Shopify activates subscription
6. Plaur unlocks features based on plan

### 8.5 Subscription Enforcement

* Subscription status is verified on every authenticated request
* Feature access is controlled via a billing-aware feature gate
* On cancellation or uninstall:

  * Access is immediately revoked
  * Data is soft-deleted as per retention policy

### 8.6 Webhooks Used

# Technical Architecture (High Level)

## Principles

* Serverless-first where it reduces ops
* Componentized microservices for analytics, ingestion, AI, and UI
* Observable and testable

## Major Components

1. **Ingestion Layer** — Webhooks, Pollers, ETL Workers

   * Shopify Webhooks & GraphQL Admin API
   * Ads pollers (Meta/Google) with backoff and idempotency
   * Trend ingestion worker
2. **Raw Storage** — Object store (S3) with partitioning per tenant
3. **Processing & ETL** — Airflow / Prefect pipelines + serverless functions
4. **Normalized Data Store** — Postgres (transactions) + columnar DB (Redshift/BigQuery)
5. **Streaming & Real-time** — Kafka/Kinesis + materialized views (ClickHouse)
6. **Feature Store & Embeddings** — Vector DB (Pinecone / Milvus) + cached embeddings in Redis
7. **AI/LLM Layer** — LLM orchestrator service, prompt templates, retriever, RAG composer
8. **API Gateway & Backend** — REST/GraphQL APIs, auth middleware
9. **Web UI** — React + Tailwind + component library; WebSocket for live updates
10. **Automation & Scheduler** — Celery / Step Functions
11. **Monitoring** — Prometheus, Grafana, Sentry, CloudWatch

### Data Flow Summary

* Data sources → ingestion → raw S3 → ETL → normalized DB / columnar store → analytics services
* Textual content & context → embedding pipeline → vector store → retriever → LLM
* UI query → API gateway → retriever + LLM → response with provenance

# AI/ML Stack & Design

## Model Choices & Hosting

> Plaur uses **Quadrant DB** for all vector search and semantic retrieval workloads, and **Sarvam API** for all voice synthesis and spoken summaries.

* **Embeddings:** Use high-quality open embeddings or cloud provider embeddings (OpenAI embeddings, if acceptable) for semantic mapping.
* **Vector DB:** **Quadrant DB** as the primary production vector database. The system will still maintain an abstraction layer to allow future portability, but Quadrant DB will be the default and optimized implementation.
* **LLMs:** Primary inference via managed LLM endpoints (OpenAI, Anthropic, or private LLMs hosted on VMs) depending on cost, latency, and data-sensitivity choices.
* **Fine-tuning vs Prompting:** Prefer RAG + prompt-engineering with minimal fine-tuning to reduce maintenance. Fine-tune only product-critical models (e.g., internal classifiers).

## Retrieval & Prompting

* **Retriever:** Hybrid BM25 + dense retriever; top-K context window with document filtering.
* **Prompt templates:** Domain-specific prompts for analytics, marketing, and trend reasoning, including system instructions that force provenance and stepwise reasoning.

## Explainability & Safety

* **Provenance:** Each claim is tagged to source documents with links to the data snapshot and query filters.
* **Hallucination mitigation:** Use conservative response templates, confidence thresholds, and include "I may be wrong" fallback behavior when confidence low.

# Security, Privacy & Compliance

## Data Handling

* **Encryption:** TLS in transit, AES-256 at rest.
* **Isolation:** Tenant scoping via separate DB schemas or row-level security; encryption keys per tenant.
* **Retention:** Default retention 2 years for analytics; configurable.

## Compliance

* **GDPR:** Data subject access and deletion processes; data export
* **PCI:** Do not store credit card data; rely on Shopify’s PCI environment
* **SOC2 readiness:** Logging, incident response, documented processes

## Access & Secrets

* **Secret management:** AWS Secrets Manager / HashiCorp Vault
* **Least privilege:** OAuth scopes for each integration; support granular revocation
